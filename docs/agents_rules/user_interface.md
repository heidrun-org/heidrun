# User interface of Heidrun

This document says where each part of the window goes and how each part works. The words are defined in [glossary.md](glossary.md). The layout below is the layout of the window.

## Layout

```
┌───────────┬─────────────────────────────────────┬───────────┐
│           │ [tab 1] [tab 2] [+]                 │           │
│   left    ├─────────────────────┬───────────────┤   right   │
│  sidebar  │ panes of the        │ pinned panes  │  sidebar  │
│           │ selected tab        │ in a column   │           │
│           │                     │               │           │
├───────────┴─────────────────────┴───────────────┴───────────┤
│ status bar: [● heidrun] [status bar section] [...]          │
└─────────────────────────────────────────────────────────────┘
```

## Rules of the layout

- The viewport gets the most width, because the developer reads and writes text there.
- The left sidebar, the viewport, and the right sidebar are three frames of the same kind: the same border, the same rounded corners, and the same background. The tab bar is inside the frame of the viewport.
- A part that the developer uses rarely does not take space all the time. A part that the developer uses often is always visible.

## Text that must stay on one line

- A piece of information that must not go to the next line, for example a folder path, a file path, or a Git branch name, is always shown on one line.
- When the container is too narrow to show the whole text on one line, the text does not wrap and does not break in the middle of a word. The container cuts the text at its edge.
- While the pointer is over the container, the text scrolls sideways, so that the developer can read the whole text.
- The folder path in the information card of the Workspace status bar section follows these rules ([issue #303](https://github.com/heidrun-org/heidrun/issues/303)).

## Files

- Heidrun never modifies a file of the developer. Only the coding agents that run in the panes modify files.
- A part of the window that shows files, for example a file explorer, only reads them. It has no button to create, rename, move, delete, or edit a file.

## Workspace

- One workspace is selected at a time.
- The workspace status bar section is the first status bar section, at the left end of the status bar. It shows a status dot and the name of the selected workspace. A click on it opens its information card above the section. The information card does not open when the mouse moves over the section.
- The status dot is always visible, and it sits before the name, in the same place as the dot of a tab. When an agent in another workspace is blocked or has finished, the dot has the color of that status, and it follows the cards of the Needs you sidebar section. Otherwise, the dot shows the status of the selected workspace. A workspace without an agent gets a hollow ring.
- The information card of the workspace status bar section gives the folder, the Git branch, the number of tabs, and the number of agents of the selected workspace. Under the details, it lists the workspaces. A click on a workspace selects it, and closes the information card.
- The list of workspaces has no separator line between the workspaces, and no space between two rows: between the two separator lines, the pointer is always on a workspace. Each row is 32 pixels tall, with the padding inside the row. One separator line sits between the list and the entry "New workspace…" at the end of the information card.
- The line after the workspace status bar section has 6 more pixels of space on each side than the other lines of the status bar, so that the workspace status bar section is not packed against the next status bar section.
- Each workspace of the list offers the rename of the workspace, the close of the workspace, and the move of the workspace by drag and drop. The rename puts a text field in the place of the name in the status bar. A double click on the workspace status bar section does not rename the workspace.
- Two other ways to switch workspace: the command search with ⌘K, and the shortcut Option+Command+Up arrow or Option+Command+Down arrow.

## Tabs

- The tab bar sits at the top of the viewport, inside its border. It shows the tabs of the selected workspace, one entry for each tab. It has no workspace selector: the workspace status bar section has it.
- A click anywhere on a tab, padding included, selects the tab. The viewport then shows the panes of that tab. The close button of the tab is the only exception: a click on it closes the tab.
- The plus button at the end of the tab bar creates a new tab.
- The developer reorders the tabs by pressing a tab, moving the mouse, and releasing the button where the tab goes. The same holds for the list of workspaces and for the list of notes. The reorder uses the pointer events of the page, and never the drag and drop of the browser: the window of Heidrun receives the image files that the developer drops from Finder, so the native window takes every drag and drop, and the page gets no drag event of the browser. A press that moves less than 5 pixels is a click. The key Escape cancels the move.
- A developer switches tab often, so the tabs are always visible.
- A workspace has few tabs, twenty tabs is extremely rare. So each tab is large, with generous horizontal padding.
- Each tab shows a small icon between its status dot and its name: the Claude icon, the OpenAI icon for Codex, or the terminal icon. A pane with an agent always beats a terminal. Among the panes with an agent, the pane that decides the color of the status dot gives the icon (blocked, then working, then done, then idle). When two panes have the same status, the selected pane wins, then the focused pane, then the first pane.
- The shortcut Option+Command+Left arrow or Option+Command+Right arrow selects the previous or the next tab.

## Panes

- A tab with one pane shows one terminal over the whole viewport.
- A tab with several panes shares the viewport between its panes.
- A click on a pane gives the focus to that pane.
- A click on the pin button in the header of a pane pins the pane. A pinned pane goes into the column of pinned panes.
- The column of pinned panes sits at the right edge of the viewport, beside the panes of the selected tab. It shows every pinned pane in every tab, the tab of the pinned pane included. Its width is the same in every tab, so a pinned pane keeps the same width in every tab.
- The panes of the selected tab that are not pinned fill the width that the column leaves. A tab whose panes are all pinned shows the same picture as an empty tab.
- The header of a pinned pane in the column shows the pressed pin button, as in the panes of the selected tab. A click on the pressed pin button unpins the pane.
- A pinned pane does not change when the developer selects another tab or another workspace. Only the panes of the selected tab change.

## Needs you

- The Needs you sidebar section is a sidebar section of the right sidebar. It holds one card for each agent that is blocked, that asks a question, or that has finished, with the blocked agents first.
- A click on a card shows the pane of the agent. A card also lets the developer answer a blocked agent, pin the pane, and hide the card.
- The button of the Needs you sidebar section shows the number of cards. The number is red when an agent is blocked.
- A hidden card comes back at the next change of the agent. A finished agent leaves the sidebar section after the delay that the settings give.

## Sidebars

- A sidebar holds several sidebar sections, and shows one sidebar section at a time.
- The left sidebar holds the Scripts sidebar section and the Source control sidebar section.
- The right sidebar holds the Needs you sidebar section, the Notes sidebar section, and the Chats sidebar section.
- Each sidebar has a sidebar icon bar, always visible, like the bar of icons of Visual Studio Code. The sidebar icon bar sits at the outer edge of the sidebar: at the left of the left sidebar, and at the right of the right sidebar. The two sidebars use the same kind of sidebar icon bar.
- The sidebar icon bar shows one icon for each sidebar section, one under the other: `play-circle` for the Scripts sidebar section, `git` for the Source control sidebar section, `bell` for the Needs you sidebar section, `sticky` for the Notes sidebar section, and `chat-left-text` for the Chats sidebar section. The title of the sidebar section is the tooltip of its icon. The number of a sidebar section sits on the top right corner of its icon.
- A sidebar is expanded or collapsed. An expanded sidebar shows the sidebar icon bar and the content of the selected sidebar section, side by side, in one frame, with a line between them. The icon of the selected sidebar section has a background. A collapsed sidebar shows only the sidebar icon bar, 48 pixels wide, and no icon has a background.
- A click on the icon of the sidebar section that an expanded sidebar shows collapses the sidebar. A click on any other icon expands the sidebar, if it is collapsed, and shows that sidebar section.
- The first button of the sidebar icon bar, above the icons, collapses or expands the sidebar. In an expanded sidebar, it is the collapse button, with an arrow toward the edge of the window: `chevron-bar-left` in the left sidebar, `chevron-bar-right` in the right sidebar. In a collapsed sidebar, it is the expand button, with an arrow toward the viewport: `chevron-bar-right` in the left sidebar, `chevron-bar-left` in the right sidebar. The expand button expands the sidebar to its selected sidebar section.
- A collapsed sidebar has no line to drag: its width does not change. The width of an expanded sidebar includes the sidebar icon bar.
- A button hides each sidebar completely, collapsed or not. A hidden sidebar leaves no strip of icons, so the viewport takes the whole width. When the sidebar shows again, it is collapsed or expanded as before.
- The two hide buttons are of the same kind, and sit in the top bar: the button of the left sidebar at the left, and the button of the right sidebar at the right. The shortcut ⌘B hides or shows the left sidebar, and the shortcut ⌥⌘B hides or shows the right sidebar.
- When the developer or the code opens a sidebar section, for example the Notes sidebar section after the shortcut ⇧⌘P pins a text, the sidebar that holds the sidebar section opens if it is hidden, and expands if it is collapsed to the sidebar icon bar. A sidebar that holds another sidebar section does not change.
- The sidebars hold no tabs. The word "tab" belongs to the tab bar only.

## Source control

The Source control sidebar section copies the source control view of VS Code ([issue #305](https://github.com/heidrun-org/heidrun/issues/305)).

- The Source control sidebar section shows only the local Git repository. It shows nothing of GitHub or GitLab.
- The header holds the title "Source Control" and three buttons that show only an icon: "Commit" (a check mark), "Refresh", and "More actions" (three dots: Pull, Push, Fetch, and the large Git window).
- The commit message box fills the full width. Its placeholder text names the current branch: `Message (⌘Enter to commit on "dev_jerome")`. The keys ⌘Enter make the commit. The sparkle button at its right asks a coding agent (`codex`, else `claude`) to write the message from the diff of the staged files, or of every change when nothing is staged.
- The blue commit button fills the full width. The arrow at its right opens a dropdown menu: "Commit", "Commit and push", and "Commit (amend the last commit)". When no file is staged, a confirmation asks to stage every change and commit it. After a commit, the message box is empty.
- The group "Staged Changes" shows only when a file is staged. The group "Changes" holds the files that are not staged, the new files, and the files in conflict. A file staged then changed again is in the two groups. Each group header has an arrow that folds the group, the title, and a badge with the number of files.
- The buttons of a group header and of a file line show only while the pointer is over the header or the line. On "Staged Changes": Stash, View the changes, Unstage all. On "Changes": Stash, View the changes, Discard all, Stage all. On a file line of "Changes": Open the file, Discard, Stage. On a file line of "Staged Changes": Open the file, Unstage.
- A file line shows the icon of the kind of the file, the file name, its folders in grey (nothing for a file at the root of the repository), and a colored status letter at the right: M modified, A added, D deleted, R renamed, U untracked, ! conflict. Its tooltip gives the full path and the status in words. A click on the line opens the diff of the file in the large Git window.
- A discard asks for a confirmation first, because the changes cannot come back. A file that Git does not know is deleted.
- The icon of the Source control sidebar section in the sidebar icon bar shows the number of changed files.

## Notes

- A note belongs to the workspace where the developer pinned the text. The workspace is found again by its name, because Herdr gives new identifiers to its workspaces in its next session.
- The Notes sidebar section lists the notes of the selected workspace, or every note when "All workspaces" is checked. The number on the button of the Notes sidebar section counts the notes that the list shows.
- A note whose workspace does not exist any more stays, and shows only when "All workspaces" is checked.

## Chats

- The Chats sidebar section is a sidebar section of the right sidebar. It lists the chats of the selected workspace.
- The folder of the selected workspace gives the chats: the root of the repository that holds the folder of the workspace. A chat that a coding agent saved for another folder, a worktree of the workspace included, is not in the list.
- The top of the Chats sidebar section is one line with two Bootstrap radio button groups (`btn-group` with `btn-check` inputs) and the button of the Chats sort dropdown menu. At the left, one button for each coding agent that Heidrun supports, Claude and Codex, with its name. A button is disabled, with a title that says why, when the selected workspace has no chat of that coding agent. At the right, first the button of the Chats sort dropdown menu, then the second group with two buttons that show only an icon, with a title: the expanded view (the icon `view-stacked`), and the compact view (the icon `list`). The checked button of a group has the background `--bs-secondary-bg`, and the other buttons have no background. The Chats sidebar section shows no group when neither coding agent has a chat, and says so. The line of the two groups and the button of the Chats sort dropdown menu, the dynamic topic bar, and a separator line (as wide as the sidebar) form the header of the Chats sidebar section. The header stays at the top of the Chats sidebar section while the list scrolls under it (`position: sticky`, with the background of the sidebar).
- The compact view is the first look of the list: the rows are tight. The expanded view gives more air: each row has more space above and below it, and the three lines of its summary are farther apart. The coding agent and the view that the developer chose are saved in the settings (`chatsAgent` and `chatsView`), and the next start uses them.
- The Chats sort dropdown menu sits at the right of the top line, at the left of the group of the two view buttons. Its button is a Bootstrap `btn dropdown-toggle` that shows the icon of the chosen order (`sort-down` for "Descending", `sort-up` for "Ascending"), the name of the chosen sort key (for example "Issues"), and the Bootstrap caret. The icon alone shows the order, and the text alone shows the sort key. The button shows no spinning wheel: the icon never changes while a new sort waits for its answer, and the list stays on the screen until the new list arrives. A click on the button opens a Bootstrap `dropdown-menu` under the button, with its right edge on the right edge of the button. The window places it (`position-fixed`, in the body of the page), so the sidebar never cuts it. The dropdown menu has two parts, each one with a `dropdown-header`, and a `dropdown-divider` between them. Each item is a `menuitemradio` with a check mark at its left (the icon `check2`, hidden with `invisible` on the items that are not chosen, so every text starts at the same place).
  1. "Sort by": "Created on" (the date of the first record that has a date, or the date of the file when no record has a date), "Last updated" (the date of the file of the chat), "Messages from you" (the number of messages that the developer typed), "Issues" (the number of issues that the chat mentions), "Pull requests" (the number of pull requests that the chat mentions), and "Files written" (the number of different files that the coding agent wrote, a file of a worktree and the same file at the root counting as one).
  2. "Order": "Ascending" (the icon `sort-up`) and "Descending" (the icon `sort-down`). The order applies to the sort key that was chosen: "Ascending" puts the smallest value first (the oldest date, or the smallest number), and "Descending" puts the largest value first (the newest date, or the largest number). Chats with the same value keep the chat with the most recent activity first.
  A click on an item chooses it, closes the dropdown menu, and reads the list again with the same number of chats. The key Escape, a click outside, and a second click on the button close the dropdown menu without a choice. The sort key and the order are saved in the settings (`chatsSortKey` and `chatsOrder`), and the next start uses them. The two choices are the same for Claude and for Codex. The items "Total comments", "Best match", and "Reactions" of the GitHub dropdown menu are not here, because a chat has no such fact. The Tauri command `chats_list` receives `sortKey` and `order`, and does the sort.
- Below the separator, the list shows the title of each chat of the chosen coding agent, in the order of the Chats sort dropdown menu. The first start gives the sort key "Last updated" and the order "Descending": the chat with the most recent activity is first. The title of Claude comes from the last title record of the file of the chat. The title of Codex comes from the index of Codex. A chat without a title shows its first message. A chat without a title and without a message is not in the list.
- Each row of the list has a Bootstrap button group at the right of its title, with two buttons that show only an icon, each with a title. The first button (the icon of the coding agent, as the tabs show it: `claude` for Claude and `openai` for Codex; the title is "Open in the Claude app" or "Open in the Codex app") opens the chat in the desktop application of the coding agent, with the address `claude://code/<session identifier>` or `codex://threads/<session identifier>`. The second button (the icon of Heidrun, the goat: `heidrun-goat-only` of the component `Icon`, drawn from `data/images/heidrun_icon_goat_only.svg`; the title is "Open in Heidrun") opens a new tab of the selected workspace, named after the chat, in the folder of the workspace, and types `claude --resume '<session identifier>'` or `codex resume '<session identifier>'` in it. A session identifier with a character other than a letter, a digit, or a dash is refused, so that no shell command can be built from it. The address of Codex comes from its documentation; the address of Claude is documented for the mobile application only, so the Claude button is not proven in the desktop application. The capability `opener:allow-open-url` allows only the schemes `claude://` and `codex://` besides the default ones.
- The list shows 5 chats at the start. Under the list, two buttons stay visible all the time: "Show more" on the left and "Show less" on the right. "Show more" is disabled when the workspace has no more chats of the chosen coding agent. "Show less" is disabled when the list has no more chats than the next lower number allows. Each click on "Show more" asks for more: 10 chats, then 20, then 50, then 50 more at each click. Each click on "Show less" goes one step back, down to 5 chats, and cuts the list at once without reading the files again. While "Show more" waits for the answer, it shows a small spinning wheel at its right end, close to the right border, and both buttons are disabled. The wheel sits on top of the button and takes no room, so neither button changes its size or its place when the wheel appears or goes away. The label of each button stays in the center. The wheel is centered with `top-0 bottom-0 my-auto`, never with a `transform`: a utility class with `transform` and `!important` stops the rotation of the wheel. With the sort key "Last updated", the program opens only the files of the chats that the list shows, so the cost does not grow with the number of chats of the workspace. With every other sort key, the program opens every file of the chats of the workspace, because the sort needs what each file holds, and keeps what it read in the cache: the first read of a large workspace is slower, and the next reads open only the files that changed. The one exception is the first line of each file of Codex: the program reads it once, to know the folder of the file, and keeps it. The list starts again with 5 chats when the developer selects another workspace.
- The rows of the list use the Bootstrap list group. The separators between the rows go from one edge of the sidebar to the other, and the title and the lines of a row keep the same small margin as the selector (14 pixels) at the left and at the right. A row gets a background while the mouse pointer is over it.
- Under the title, each chat shows a summary in muted color, in up to three lines. A line has no indent: its icon starts at the same place as the first letter of the title. A line that has nothing to say is left out. Each line starts with a small icon.
  1. The clock icon, then the first and the last date, then the number of messages from the developer.
  2. The icon of the forge of the repository (GitHub or GitLab, else the Git icon), then the issue numbers, then the pull request numbers. A list of numbers shows the first three, then "+" and how many more.
  3. The file icon, then the names of the first two files that the coding agent wrote, then "+" and how many more. This line is the files line.
  The folders where the coding agent ran are found and kept, but the summary does not show them yet.
- The files line has an information card. The files line gets a background while the pointer is over it, and the information card opens at the left of the files line on a click, or on the key Enter or the key Space when the files line has the keyboard focus. A press on a row of the list does not change the background of the row. The background of the files line stops at the end of the widest of the three lines of the summary, and does not go to the edge of the column. The information card does not open when the pointer only moves over the files line. The program places the information card again each time its height changes (for example when a row expands) and each time the window changes its size, so the information card never goes out of the window. The information card stays open until a second click on the files line, the key Escape, a click outside, or the loss of the keyboard focus closes it.
- The information card has a title with the files icon and the number of files written, then one row for each file. A row shows an icon that fits the kind of the file, then two lines: the name of the file in medium weight, and the folders of the file in muted color under it. A file at the root of the repository shows `./` as its folders, so every row has two lines. A line that does not fit shows its beginning with an ellipsis, on one line. While the pointer is over the row, a line that does not fit scrolls to its end, after a short wait, and it shows its beginning again when the pointer leaves. The scroll is a CSS transition of the transform of the text, at a constant speed, so the browser moves the text by fractions of a pixel without JavaScript frames. At the right of the row, a Bootstrap button group holds two buttons that show only an icon: the VS Code icon, and the GitHub or GitLab icon. Each button has a title that says what it does, without the path of the file: "Open in VS Code" and "Open in GitHub". A button gets a background, lighter than the background of the row, while the pointer is over it. A row gets a soft background while the pointer is over it, and the files line and the buttons get a stronger background than the soft one, so each of them still shows inside the row. The soft background is the color `--hover-soft`, for every row of a Bootstrap list group. The information card uses the Bootstrap list group, so its rows are like the rows of the list.
- The folders of a file are the path below the root of the repository. A file that the coding agent wrote in a worktree of the repository (a path that starts with `.claude/worktrees/<name>/` below the root) shows the path of the same file at the root, because the worktree is deleted after its merge. A file written in a worktree and the same file at the root count as one file, in the files line and in the information card. A file that is not below the root of the repository shows its absolute path, and its two buttons are always visible but disabled, with the title "Cannot open the file: it is not in the repository."
- "VS Code" opens the file at the root of the repository, after it checks the file against the folder of the selected workspace. "GitHub" or "GitLab" opens the file on the web page of the repository, on the default branch (`HEAD`). Every row always shows its buttons. A repository without a remote has no button for the forge. A button that fails shows the reason in a message.
- Each time the information card opens, the program tells which files exist (the Tauri command `chats_files_exist`). "VS Code" is disabled when the file is not in the working folder of the root of the repository. "GitHub" or "GitLab" is disabled when the file is not on the default branch of the remote. The default branch is `refs/remotes/origin/HEAD` as the last fetch knows it, or `HEAD` when the repository has no such reference. The check is local and offline. A disabled button shows the reason in its title when the pointer rests on it. When the check fails, the buttons stay on.
- The references line has an information card, opened the same way as the information card of the files line: the whole line is the part that gets a background under the pointer, and a click on the line opens the information card. A repository without a remote has no forge to read, so its references line has no information card.
- The information card of the references line has a title with the icon of the forge and the text "Issues and pull requests", then one row for each issue, then one row for each pull request. A row shows an icon (a circle with a dot for an issue, the Git icon for a pull request), the title in medium weight, the name and the state in muted color under it ("Issue #250 · Closed"), and a chevron. While the forge is read, the name stands for the title. A line that does not fit scrolls like the lines of the files card.
- A click on a row opens its details under the row, one row at a time, and a second click on the row closes them. The details copy the layout of the card that GitHub shows: the repository and the date of the creation ("heidrun-org/heidrun on Oct 11"), the state in a pill (green for open, purple for merged, purple for a closed issue, red for a closed pull request), the beginning of the description as plain text in at most five lines, the labels of an issue in their colors or the two branches of a pull request (the receiving branch, an arrow, then the branch with the changes), and the person who opened it. Two icon buttons sit at the right of the state: "Open in Heidrun" (the goat icon of Heidrun) opens the description and the comments in the issue window of Heidrun, and "Open in GitHub" (or "Open in GitLab") opens the web page.
- Each time the information card of the references line opens, the program reads every row from the forge with `gh` or `glab`, four rows at a time, through the Tauri command `forge_cli_cached`. The Tauri command keeps each answer on the disk, in `forge_cache.json` in the folder of the data of Heidrun, for ten minutes, so a second opening is immediate and a failure of the network does not empty the rows: an answer that is at most seven days old replaces a failure.
- The dates line has an information card, opened the same way as the information card of the files line: the whole line is the part that gets a background under the pointer, and a click on the line opens the information card.
- The information card of the dates line has a title with the clock icon and the text "Dates and messages", then one row for each fact, with the name of the fact in muted color at the left and its value at the right: "Started" and "Last activity" say how long ago the date was with one unit ("2 days ago", "Just now" under one minute), and each one ends with a small question mark (the HTML tag `small` around the icon `question-circle`) whose title is the full date with the day of the week and the time; "Duration" has one unit, rounded to the nearest ("12 minutes", "3 hours", "Less than a minute"); and "Messages from you" is the number of messages. A fact that the chat does not have is left out. The text "ago" is made again each time the information card opens. A muted row "Your first messages" follows, then one row with a chat icon for each of the first three messages that the developer typed, in order, each one on one line of text cut to 300 characters by the program. A row of a fact and a row of a message get the soft background while the pointer is over them, like the rows of the other information cards of a chat. The information card shows no folder and no file: the files line shows the files. The name of a fact stays on one line.
- Every information card of a chat is 34 rem wide, and narrower when the window leaves less room at the left of its part. A list in an information card that is taller than half of the window scrolls. Its scroll bar is thin (10 pixels, with a thumb of 6 pixels), its track is transparent, and its thumb is very dim while the pointer is not over the list, a little brighter while the pointer is over the list, and brighter again while the pointer is over the thumb. The scroll bar is made with the `::-webkit-scrollbar` pseudo-elements, in `InformationCard.vue`, so every list of an information card has the same scroll bar.
- The program finds the summary without a model, by reading the file of the chat: the dates come from the `timestamp` field of the records, the messages from the records that the developer typed (the program also keeps the text of the first three, on one line, cut to 300 characters), and the files from the Write, Edit, MultiEdit, and NotebookEdit tools of Claude and from the patches of Codex. A pull request number comes from the `pr-link` records of Claude, from addresses that end with `/pull/<number>`, and from the words "pull request" or "PR" before a number. An issue number comes from addresses that end with `/issues/<number>`, from the word "issue" before a number, from `gh` commands, and from a bare `#<number>` in a message of the developer or in a commit command. A number that is a pull request is never an issue.
- The program keeps what it read in each file in the file `chats_cache.json`, in the data folder of Heidrun. It reads a file again only when the size or the modification date of the file changes. A file that only grew is read from the place where the last read stopped, so a long chat that is still running costs little.
- The Settings window has a section "Dynamic topics", the last section of its sidebar (icon `tags`). The section holds the choice "Extraction method": two radio buttons, "Keyword" and "Language model". The choice is the option `dynamicTopicExtraction` of the settings, and the default is "keyword". Both radio buttons are enabled. The title of the radio button "Language model" says that the coding agent `codex` or `claude` that is installed on this computer finds the topics. The more menu has no entry for it.
- The title "Extraction method" is followed, on the same line, by a circled question mark (the icon `question-circle`, in muted color). The section has no help paragraph under the radio buttons: the circled question mark holds the help. A click on it opens an information card below it, with a title (the question mark icon and the text "Extraction method"), then two blocks: "Keyword" says that the topics of each chat come from the words of its title, of the first messages that the developer typed, of the folders of the files that the coding agent wrote, and of the titles of its issues and pull requests, and that nothing leaves this computer; "Language model" says that a language model finds the topics, and that Heidrun sends the title and the first messages that the developer typed, of the chats that the list shows, and nothing else, to the coding agent `codex` or `claude` that is installed on this computer. Each block has its name in the medium weight, and its text in muted color.
- The section "Dynamic topics" of the Settings window has a second part, "Clustered dynamic topics": a Bootstrap switch (`form-check form-switch`) with the label "Enable clustered dynamic topics", a circled question mark just after the label, and a button "Rebuild the clusters". The switch is the option `clusteredDynamicTopics` of the settings, and the default is off, because the method makes calls to a coding agent. The part has no help paragraph under the switch. A click on the circled question mark opens an information card below it, with a title (the question mark icon and the text "Clustered dynamic topics"), then three blocks: "What it is" (a clustered dynamic topic is the name of a group of dynamic topics that have a close meaning, so one subject has one label), "What Heidrun sends" (only the short labels of the raw dynamic topics, and never the text of a chat, to the coding agent `codex` or `claude` that is installed on this computer), and "When the option is off" (Heidrun shows the raw dynamic topics and makes no call). The button is disabled while the option is off and while a call runs, and it shows a Bootstrap spinning wheel while a call runs. A line under the button says why the last call gave no cluster (no coding agent, a failure, or a wrong answer), only while the option is on.
- The information card of a circled question mark in the Settings window follows the rules of every information card: it opens on a click, and a second click on the circled question mark, the key Escape, a click outside, and the loss of the keyboard focus close it. It opens below the circled question mark, with its arrow under the middle of the circled question mark, and it stays inside the window. The component `InformationCard` has the property `placement` for this: "start" (the default) opens the card at the left of its part, and "bottom" opens it below.
- While the option "Clustered dynamic topics" is off, the dynamic topic bar and the topics on the row of each chat show raw dynamic topics, and Heidrun makes no call. While it is on, both show clustered dynamic topics, so a button of the dynamic topic bar matches what the rows show, and a click on a button shows only the chats that have the cluster. A raw dynamic topic that the translation table does not know yet is shown as its own cluster, until the table has its row.
- The clusters come from the translation table, the file `topic_clusters.json` in the data folder of Heidrun: it maps each raw dynamic topic, in lower case, to the name of a cluster. Chats of Claude and of Codex share one table, because a raw dynamic topic does not depend on the coding agent. A row is never changed, and never leaves the table, except at a rebuild. At each run, Heidrun finds the raw dynamic topics of the chats that the list shows, after the keyword topics are ready, and that the table does not know. When there is none, or when the option is off, Heidrun makes no call. Otherwise it makes one single call to a coding agent, through the Tauri command `coding_agent_ask`, with a prompt that holds only the names of the existing clusters and the new raw dynamic topics. The coding agent is `codex` when `command -v codex` finds it in the login shell, and `claude` otherwise. When neither exists, the raw dynamic topics stay as they are. The coding agent answers with a JSON array that has one item `{"topic", "cluster"}` for each new raw dynamic topic, and a name of one or two words for each cluster. Heidrun saves the rows only when each new raw dynamic topic appears exactly once. A wrong answer, or a failed call, saves nothing, and the same set of new raw dynamic topics is not asked again before the next start of Heidrun, before a rebuild, or before the developer switches the option off and on.
- The button "Rebuild the clusters" empties the translation table, on the disk too, and asks for the clusters of all the raw dynamic topics of the chats that the list shows, in one call. A call that started before the rebuild saves nothing.
- Under the title of each chat, one single line shows its dynamic topics: at most three small rounded labels (Bootstrap `badge`). The line sits between the title and the summary. A chat without a dynamic topic has no line. While the method is "Language model", a chat shows its line when the language model has given its topics, and shows no line before. The topics come only from the chats that the list shows, never from the other chats of the workspace.
- The dynamic topic bar is the last part of the header, between the line of the two groups and the separator line. It shows the button "All", then one button for each dynamic topic of the chats that the list shows, the strongest first: the topic that more chats have comes first, then the topic that the chats rank higher, then the alphabetical order (`lib/dynamic_topic_bar.ts`). The buttons are small rounded labels, and the selected button has the inverted colors (the text color as background). The bar has no scroll bar, and it does not scroll by hand or by the wheel. When buttons are hidden after its visible part, an arrow with a fade shows at its end, and each click on the arrow moves the bar so that the next three topics come into view. When buttons are hidden before its visible part, the same arrow shows at its start, and each click goes back by three topics. A button that is partly under an arrow counts as hidden.
- The tooltip (the `title`) of the button of a topic gives the number of chats of the list that have the topic, for example "Show only the chats about “panel” (2 chats)". The number is never written on the button itself, and it stays the same while a topic filters the list.
- Each topic label on the row of a chat is a button (Bootstrap `badge` on a `button`). A click on it does the same as a click on the button of the same topic in the dynamic topic bar: the list shows only the chats that have the topic, the bar marks the topic as selected, and the bar moves to show its button when the arrows hide it. A click on the label of the topic that is already selected shows every chat again, as the button "All" does. The label of the selected topic has the inverted colors, like the selected button of the bar. The tooltip of a label gives the number of chats of the topic, as the button of the bar does, and the tooltip of the selected label is "Show all the chats".
- A click on a topic of the dynamic topic bar shows only the chats that have the topic, and a click on "All" shows every chat again. The selected topic is not an option and is not saved. The bar forgets it when the developer selects another workspace or another coding agent, and when no chat of the list has the topic any more. The bar is not shown when no chat has a topic, which is the case for the method "Language model" until it has given the first topics.
- The method "Keyword" reads the dynamic topic source information of each chat: the title, the first messages that the developer typed, the folders of the files that the coding agent wrote (below the root of the repository), and the titles of the issues and of the pull requests that the chat mentioned (the three highest issue numbers and the three highest pull request numbers, read on the forge with `gh` or `glab`, four reads at a time). The messages of the coding agent are not used. It cuts the text into words in lower case, without accents, in the singular, and drops the numbers, the addresses, the words of one or two letters, and the stop words of English and of French (`lib/dynamic_topic_words.ts`). A word of the title counts 3, a word of the title of an issue or of a pull request counts 2, a word of the first messages or of a folder counts 1. The score of a word in a chat is `(1 + ln(weight)) × ln(number of chats that the list shows ÷ number of those chats that hold the word)`, so a word that every chat holds scores nothing. A list of one chat uses only the weight. The best three words, by score and then by alphabetical order, are the topics (`lib/dynamic_topics.ts`).
- The cache of the method "Keyword" is in the `localStorage` of the web frontend, under the key `heidrun.dynamicTopicsCache`. It keeps, for each chat, the identifier of the chat, the date of its last message, and the words of its dynamic topic source information with their weights, because reading the titles on the forge is the expensive part, and the best words of a chat depend on the other chats that the list shows. The topics are ranked again each time, which is cheap. A chat whose last message did not change is never read again. A new or changed chat gets its words at once from the title, the first messages, and the folders, and gets the titles of its issues and pull requests when the forge answers. A chat whose titles could not be read tries again once in the next run of Heidrun. The cache keeps the 200 chats with the newest last message (`stores/dynamic_topics.ts`).
- The method "Language model" reads the title and the first messages that the developer typed (two parts of the dynamic topic source information) of each chat that the list shows. The messages of the coding agent, the folders, the files, the issues, and the pull requests are never sent. At each run, Heidrun finds the chats that have no topics, or whose last message is newer than their topics. When there is none, or when the method is "Keyword", Heidrun makes no call. Otherwise it makes one call to a coding agent, through the Tauri command `coding_agent_ask` that the clustered dynamic topics use too (`codex` when it is installed, `claude` otherwise), for at most 20 chats. A longer list is sent in several calls, one after the other. The prompt holds the dynamic topics that already exist, the most used first and at most 100, and tells the coding agent to reuse one when it fits, so that "sidebar", "side bar", and "right panel" do not become three dynamic topics. The coding agent answers with a JSON array that has one item `{"conversation", "topics"}` for each chat, where `conversation` is the number of the chat in the prompt, and `topics` holds one to three dynamic topics of one or two words, in lower case, in English (`lib/language_model_topics.ts`). Heidrun saves the topics only when each chat appears exactly once and every topic follows these rules. A wrong answer, or a failed call, saves nothing, and the same chats at the same last message are not asked again before the next start of Heidrun, or before the developer chooses the method "Language model" again.
- The cache of the method "Language model" is in the `localStorage` of the web frontend, under the key `heidrun.languageModelTopicsCache`. It keeps, for each chat, the identifier of the chat, the date of its last message, and its topics, for the 200 chats with the newest last message (`stores/language_model_topics.ts`). A chat whose last message did not change is never sent again. A chat whose last message changed keeps its old topics on the screen until its new topics arrive, and keeps them when the call fails. The cache of the method "Keyword" and the cache of the method "Language model" are separate, so the developer can change the method without losing either one.
- Under the radio buttons of the choice "Extraction method", a line in muted color says why the last call of the method "Language model" gave no topic (no coding agent, a failure, or a wrong answer). The line shows only while the method is "Language model" and while the last call gave no topic. It is separate from the line of the clustered dynamic topics.
- The option "Clustered dynamic topics" works with both methods: the clusters are made from the raw dynamic topics of the method that the developer chose.
- The button of the Chats sidebar section shows no number.
- The list reads the chats again when the Chats sidebar section opens, when the developer selects another workspace, and every 10 seconds while the Chats sidebar section is on the screen.
- The ideas for later are in [issue #250](https://github.com/heidrun-org/heidrun/issues/250).

## Status bar

- The status bar sits at the bottom of the window, over the whole width.
- Each status bar section shows one piece of information, for example the selected workspace, the usage of Claude, the usage of Codex, the Git branch, and the connection to Herdr. The number of agents that are blocked, working, or done is not in the status bar: the top right corner of the window already shows it.
- A click on a status bar section opens its information card above the section.
- The information card of the usage of Claude and the information card of the usage of Codex are 408 pixels wide, which is 20 percent more than the 340 pixels of the other information cards of the status bar ([issue #290](https://github.com/heidrun-org/heidrun/issues/290)).

## Menu of the status item

- The status item sits in the macOS menu bar. A click on it opens a menu. From top to bottom, the menu has the line "Open Heidrun", then the three sections "Blocked", "Finished", and "Working". The menu ends with the last line of the section "Working", with no separator after it. The menu shows no quota ([issue #311](https://github.com/heidrun-org/heidrun/issues/311)).
- The picture of the status item shows only the icon of Heidrun and the three discs "Blocked", "Finished", and "Working", with little empty space around them. The picture shows no quota: the status bar of the Heidrun window shows it. On a MacBook with a camera notch, macOS hides, with no message, the menu bar icons that do not fit to the right of the notch, so the picture stays as narrow as possible ([issue #311](https://github.com/heidrun-org/heidrun/issues/311)).
- The three section titles show the normal black text with the normal weight, like "Open Heidrun" and the names of the agents. They are not gray and not bold. The lines "None" are gray.
- macOS draws every disabled menu item in gray, and no text color changes this. So the section titles are enabled menu items, and the lines "None" are the only disabled lines. The cost is that macOS turns an enabled line blue while the pointer is over it ([issue #293](https://github.com/heidrun-org/heidrun/issues/293)).
- A click on "Open Heidrun" or on a section title shows the main window. A click on an agent shows the main window and selects the pane of the agent.

## Position and size of the window

- When Heidrun quits, it saves the position and the size of the window, and whether the window was maximized or full screen. The window-state plugin of Tauri does this work, and keeps the file `.window-state.json` in the configuration folder of the application.
- At the next start, the window opens with the saved position, the saved size, and the saved maximized or full screen state.
- At the first start, no state is saved, and the window opens in the middle of the screen with the size in `tauri.conf.json`.
- When the saved position is outside every screen that is connected, the window opens at the default position of the operating system, on a connected screen.
- The visible state is never restored. The window stays hidden until the splash image is ready.

## Last state of each option

- Every option keeps its last state between two runs of Heidrun. An option is a toggle, a choice between a few values, a sidebar section that is shown, a panel that is open or closed, or a size.
- The last state of each option is saved in the `localStorage` of the web frontend, in the store `packages/apps/web_frontend/src/stores/settings.ts`, under the key `heidrun.settings`. A new option is a new line in `defaults` of this store, and not a new key.
- At the start, each option reads its saved state. An option with no saved state, or with a corrupted saved value (the wrong type, or a value that is not in the list of its values), uses its default value.
- A text that the user types, a search text for example, is not an option and is not saved. A mode that edits data, for example the edit mode of the budgets in the window History, is not an option and is not saved.

## Splash screen

- At the start, Heidrun shows the splash screen for 3 seconds after the main window appears. A click on the splash screen closes it at once.
- The splash screen has a sound button at its bottom right corner. A click on the sound button plays a goat bleat, and does not close the splash screen. See the section "Goat sounds".
- The command line option `--no-splash-screen` starts Heidrun without the splash screen. The main window then appears at once, and shows the application.
- A program that drives Heidrun, for example to take a screenshot, uses this option, so that it never waits for the splash screen to close. In development, run `pnpm dev -- -- --no-splash-screen`: the command `tauri dev` gives the arguments after its second `--` to the application, and the arguments after its first `--` to `cargo`. For the built application on macOS, run `open -a Heidrun --args --no-splash-screen` while Heidrun is not running.

## Goat sounds

- Heidrun plays two goat bleats. They are the two halves of the sound "Cabra" by sonsdebarcelona, and the files are `data/sounds/goat_bleat/goat_bleat_1.wav` and `data/sounds/goat_bleat/goat_bleat_2.wav`. The application keeps one copy of each file, and plays it from the folder `data/sounds/goat_bleat`.
- A bleat plays only after a click of the developer. No bleat plays by itself.
- Three places play a bleat: the sound button of the About modal, the sound button of the splash screen, and the smiley at the end of the joke of the empty tab screen. A click on the smiley plays a bleat only when it starts the laugh again, so the laugh that starts by itself stays silent, and a click while the laugh is still running plays nothing.
- The bleats play in turn: the first click plays the first bleat, the second click plays the second bleat, the third click plays the first bleat again. The three places share the same turn. A bleat that is still playing stops when the next bleat starts.
- The license of the sound is Creative Commons Attribution NonCommercial 3.0, so the About modal shows the credit to the author, with a link to the Freesound page.
